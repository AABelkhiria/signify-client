# signify-client

The Signify client in Rust: boot and connect to a KERIA agent, send it signed requests, and drive
every endpoint family and workflow the agent offers. The behavior and wire bytes match
[signify-ts](https://github.com/WebOfTrust/signify-ts), checked against fixtures it generates.

This crate is the SDK's single entry point. The crates it is built on are re-exported at the root,
so an application depends on `signify-client` alone and never names a `keri-*` crate directly.

## Modules

| Module | Purpose |
|---|---|
| `config` | What a client is built from: admin and boot URLs, passcode, security tier |
| `client` | The lifecycle: boot an agent, read its state, connect, send signed requests |
| `endpoint` | The KERIA endpoint families: identifiers, key events and states, registries, schemas, credentials, IPEX, notifications, OOBIs, challenges, contacts, escrows, exchanges, groups, operations, agent config |
| `operation` | Waiting for a long-running agent operation to finish |
| `multisig` | Bringing a multisig group into existence and running it afterwards |
| `presentation` | Disclosing a credential over IPEX, and asking for one |
| `random` | The passcode and nonce a client draws from the operating system |
| `error` | What a client lifecycle can fail at |

Re-exports: `keys` (signify-keys), `http` (signify-http), `protocol` (keri-protocol), `acdc`
(keri-acdc), `cesr` and `crypto` (keri-cesr), `auth` (keri-http-auth) and `types` (keria-types).

Nothing here implements protocol logic of its own. Events come from `signify-keys`, credentials
from `keri-acdc` signed through `signify-keys`, and the signed-request mechanism from
`signify-http`. What the client adds is which URL to send to, which prefix to stamp, and which key
to verify against.

## Features

- `http-client`: the production transport, built on hyper, rustls and tokio. Off by default so a
  library that only builds and signs requests carries no TLS stack.

## Use

```bash
cargo add signify-client --features http-client
cargo add tokio --features macros,rt-multi-thread
```

```rust
use std::sync::Arc;

use signify_client::client::SignifyClient;
use signify_client::config::ClientConfig;
use signify_client::http::request::ItemRange;
use signify_client::http::retry::TokioClock;
use signify_client::http::transport::HttpTransport;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = ClientConfig::new("https://keria.example.org:3901", "0123456789abcdefghijk")?
        .with_boot_url("https://keria.example.org:3903")?;
    let transport = Arc::new(HttpTransport::new()?);
    let client = SignifyClient::new(config, transport, Arc::new(TokioClock))?;

    client.boot().await?;
    let connected = client.connect().await?;

    let listing = connected.identifiers().list(ItemRange::DEFAULT).await?;
    println!("{} identifiers", listing.identifiers.len());
    Ok(())
}
```

Connecting is a type change: `connect` consumes the `SignifyClient` and returns a
`ConnectedClient`, which is the only type that can send a signed request. Tests swap the transport
for `signify_client::http::transport::ScriptedTransport` and the clock for a `TestClock`, so every
request a workflow sends can be recorded and compared without a network.

## Reference fixtures

`fixtures/` holds the recorded requests and answers that the tests in `tests/` assert against,
generated by signify-ts and keripy at the pins in `tools/reference-vectors/` at the repository
root. Each fixture directory has a README with its provenance.
