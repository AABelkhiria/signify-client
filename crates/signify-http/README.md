# signify-http

HTTP for the Signify client: what a request and a response are, who sends them, how a request is
signed and a response verified, and how a failed request is retried. The wire bytes match
[signify-ts](https://github.com/WebOfTrust/signify-ts), checked against fixtures it generates.

Part of [signify-client](https://crates.io/crates/signify-client), which re-exports this crate as
`signify_client::http`. Depend on `signify-client` unless you only need the transport layer.

## Modules

| Module | Purpose |
|---|---|
| `transport` | The `Transport` trait, `Request`, `Response`, `RequestUrl`; a `ScriptedTransport` for tests; `HttpTransport` behind the `http-client` feature |
| `request` | Building one request: a URL from a base and typed components, a body that names its type, `ItemRange` for paged reads |
| `response` | Reading one response: status, typed body, `Content-Range` position in a paged list |
| `signature` | HTTP message signatures around a request in flight, on the primitives from keri-http-auth |
| `retry` | How long to wait, when to stop, who gets told; the `Clock` trait with `TokioClock` and `TestClock` |
| `header` | Validated header names, values and collections, from keri-http-auth |

The `Transport` trait is `dyn`-compatible on purpose: a client holds one `Arc<dyn Transport>` for
its whole life, a production implementation in a binary and a scripted one in a test, with no
generic parameter spreading through every endpoint family.

## Features

- `http-client`: `HttpTransport`, built on hyper, rustls and tokio. Off by default so the rest of
  the crate builds without a TLS stack.

## Reference fixtures

`fixtures/` holds the recorded requests, signatures and retry schedules that the tests in `tests/`
assert against, generated by signify-ts at the pin in `tools/reference-vectors/` at the repository
root. Each fixture directory has a README with its provenance.
