# signify-keys

Key management for the Signify client: keepers that create, store, rotate and sign with keys, the
identifier habitats built on them, the client's own controller identity, and the ACDC artifacts
those keepers sign. Everything is pure state: nothing here performs I/O, reads a clock, or knows a
KERIA endpoint. The behavior and wire bytes match
[signify-ts](https://github.com/WebOfTrust/signify-ts), checked against fixtures it generates.

Part of [signify-client](https://crates.io/crates/signify-client), which re-exports this crate as
`signify_client::keys`. Depend on `signify-client` unless you only need the key layer.

## Modules

| Module | Purpose |
|---|---|
| `manager` | Key creation, storage, rotation and signing for the identifiers one controller manages; the `IdentifierKeeper` |
| `identifier` | Local identifier habitats and the `Habery` that turns key-manager inceptions into complete inception events |
| `controller` | The client controller derived from a passcode, its inception, delegation approval and passcode rotation; the KERIA `Agent` it delegates to |
| `acdc` | Issuing and revoking a credential against the issuer's KERIA key state, and the IPEX messages a client sends, on the builders in keri-acdc |

The KERI protocol messages come from `keri-protocol`, which callers reach directly.

## Reference fixtures

`fixtures/` holds the recorded keys, events and signatures that the tests in `tests/` assert
against, generated by signify-ts at the pin in `tools/reference-vectors/` at the repository root.
Each fixture directory has a README with its provenance.
